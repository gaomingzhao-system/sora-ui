# Architecture

## Goals and constraints

- Every project-owned component compiles in **Vue Vapor mode** (`<script setup lang="ts" vapor>`)
  with Vue `3.6.0-rc.15`. No virtual-DOM component, no `h()`, no JSX, no Options API, no mixins and
  no private Vapor internals. [`pnpm check:vapor`](../scripts/check-vapor.ts) enforces this.
- A traditional component API: props for behaviour and variants, `v-model` for state, named and
  scoped slots for content. Components are complete on their own; nothing is assembled from
  compound primitives.
- The browser does the hard parts: `<dialog>.showModal()`, the Popover API, CSS anchor positioning,
  native inputs, `:has()`, container queries, `light-dark()`.
- Usable without Tailwind and friendly to a Tailwind v4 host.

## Packages

```text
@your-scope/theme   no dependencies, platform neutral
@your-scope/ui      depends on @your-scope/theme; peer: vue (exact RC)
                    optional peers: @formisch/vue, valibot, petite-vue-i18n
```

### `@your-scope/theme`

Pure TypeScript: the built-in OKLCH palettes, `defineSoraConfig()`, the resolver that turns a
configuration into `--sora-*` custom properties, and a contrast audit. It is used at build time by
`pnpm generate:theme` and at run time, on demand, through `@your-scope/ui/theme`.

### `@your-scope/ui` entry points

The export map is explicit (59 subpaths, generated by
[`scripts/sync-exports.ts`](../scripts/sync-exports.ts) from the manifest) and ESM only.

| Entry                              | Contents                                               | May import                 |
| ---------------------------------- | ------------------------------------------------------ | -------------------------- |
| `@your-scope/ui`                   | 42 core components, composables, icons, types          | `vue`                      |
| `@your-scope/ui/components/<Name>` | one component as the default export                    | same as its family         |
| `@your-scope/ui/forms`             | `SoraForm`, `SoraFormErrorSummary`, `useSoraFormField` | `@formisch/vue`, `valibot` |
| `@your-scope/ui/i18n`              | `createSoraI18n`, `createPetiteTranslator`             | `petite-vue-i18n`          |
| `@your-scope/ui/i18n/locales/<x>`  | precompiled messages (en, ja, ar, pseudo)              | nothing                    |
| `@your-scope/ui/locales/<x>`       | the same messages as plain strings                     | nothing                    |
| `@your-scope/ui/theme`             | runtime theming helpers                                | `@your-scope/theme`        |
| `@your-scope/ui/styles.css`        | compiled stylesheet                                    |                            |
| `@your-scope/ui/tailwind.css`      | Tailwind v4 integration (token mapping and variants)   |                            |

The right-hand column is a rule, not a description: [`pnpm check:package`](../scripts/check-package.ts)
walks the JavaScript **and** the declaration graph of every entry and fails when the core reaches an
optional peer, a locale other than the built-in English fallback, or the forms code. An application
that imports only `SoraButton` and `SoraCard` therefore installs and bundles none of the optional peers
(`pnpm verify:consumer` asserts that against the packed tarballs).

## The component manifest

[`packages/ui/src/components.manifest.ts`](../packages/ui/src/components.manifest.ts) is the single
list of public components. Each entry holds the name, category, source file, public entry and the
reference notes (purpose, where attributes go, keyboard interaction, accessibility decisions, styling
hooks). It drives:

- the per-component build entries (`tsdown.config.ts`) and the export map,
- [docs/components](./components/README.md) (`pnpm docs:components`),
- the gallery's catalogue page, and the E2E test that every entry has a live demo,
- the Vapor check (every source must compile in Vapor mode).

Adding a component means: the SFC, a manifest entry, an export in `index.ts`, a gallery demo, tests.
The unit tests fail when those disagree.

## Component authoring rules

All of these were first proven in a small fixture
([`tests/fixtures/compat`](../tests/fixtures/compat), `tests/browser/compat`) before any component
was written.

**Vapor only.** `<script setup lang="ts" vapor>`. Oxlint bans the VDOM APIs of `vue`
(`no-restricted-imports`), the build passes `features: { vapor: true, optionsAPI: false }` so it
fails closed, and `check:vapor` inspects the compiled output. A Vapor component has no instance
proxy: `$attrs`, `$slots`, `$props` and `$emit` exist in templates, but `$el`, `$refs` and `$parent`
do not (they type-check and fail at run time, so `check:vapor` rejects them).

**Props.** Each component exports a `Ui<Name>Props` interface. Reactive props destructuring supplies
defaults. Size, colour and variant fall back to the nearest `SoraProvider`, then to `sora.config.ts`
(`useSoraDefaults`).

**Typed attribute passthrough.** Props interfaces `extend /* @vue-ignore */` the attribute type of
the element that receives the attributes (`ButtonHTMLAttributes`, `InputHTMLAttributes`, ...). The
runtime sees only the declared props; the type checker also accepts native attributes and listeners,
so `strictTemplates` works. Events a component emits itself are removed from that type
(`Omit<..., 'onClose'>`) so a handler is typed with the component's payload, not the native event.

**Where attributes go.** A single-element component passes attributes to its root. A wrapper control
(label + control + hint + error) uses [`useControl`](../packages/ui/src/composables/use-control.ts):
`class` and `style` customise the root, every other attribute and listener goes to the native
control. `controlAttrs` carries a binding object for the native control (Formisch's `field.props`):
listeners are composed, `aria-describedby` ids are merged, and its `ref` receives the element, then
`null` on unmount. Components with a conditional or fragment root bind `$attrs` explicitly.

**Models.** Controls declare `modelValue: T | null | undefined` and a precisely typed
`update:modelValue` event instead of `defineModel`, so "no value" is `null` and the emitted type is
exact. Overlays and navigation use `defineModel` for `open`, `page`, `sort` and similar state.

**Ids and ARIA wiring.** `useSoraId()` produces stable ids; labels, hints and errors are connected with
`for`/`aria-describedby`, merged with ids the caller supplies.

**No styles in SFCs.** Library SFCs have no `<style>` block; CSS is an explicit stylesheet import.

## Styling

Tailwind CSS v4 is a **build-time compiler** for the library, not a requirement of its users.
Templates carry semantic classes (`sora-button`) and `data-*` attributes for variants; the rules are
written in CSS files using `@apply`, `@variant` and the theme functions.

```text
packages/ui/src/styles/
  index.css              entry; declares the layer order
  theme.generated.css    tokens generated from sora.config.ts          -> @layer theme.sora
  reset.css              element resets scoped to sora-* classes      -> @layer base.sora
  components/*.css       one file per component family               -> @layer components.sora
  motion.css             transitions, @starting-style, reduced motion
  tailwind.css           shipped as-is: Tailwind integration for hosts
```

**Cascade contract.** The stylesheet starts with `@layer theme, base, components, utilities;` and puts
every rule in a sub-layer of those. Consequences:

- Unlayered application CSS always wins, without `!important`.
- In a Tailwind host, utilities override component styles whichever file is imported first, and the
  host's Preflight can never undo a component.
- Tokens are in the lowest layer, so they can be overridden from anywhere.

There is **no global reset**: `reset.css` only touches elements that carry a `sora-` class. The
compiled file contains no Tailwind variables (`--tw-*`), no un-namespaced utility classes and no
Preflight; `check:package` verifies that.

**Tokens.** All colours are `light-dark()` pairs of OKLCH values, so one stylesheet serves both
schemes and follows `color-scheme` (the default colour mode is `inherit`: the library never turns a
light page dark). Soft fills use `color-mix()`. `data-sora-theme|density|radius|motion` attributes
switch whole token groups for a subtree, which is what `SoraProvider` renders. A colour role is applied
by `data-color`, which sets a small group of local variables (`--sora-c`, `--sora-c-on`, `--sora-c-soft`,
...) that every variant reads.

## Theme pipeline

```text
sora.config.ts ──► scripts/generate-theme.ts ──► packages/ui/src/styles/theme.generated.css
                 (uses @your-scope/theme)   └► packages/ui/src/config.generated.ts
```

`pnpm generate:theme` resolves the configuration with the same resolver the runtime helpers use,
writes the token stylesheet and the runtime prop defaults, and audits contrast (currently 364 pairs
across light and dark; a failing pair fails the build). See [theming.md](./theming.md).

## Runtime context

`SoraProvider` provides one typed context: merged component defaults, the translator, the locale and
the direction. It renders a layout-neutral wrapper (`display: contents`) with the scope attributes,
or applies them to `<html>` with `target="document"`. Nested providers merge; nothing is global.

## Internationalisation

Components know one tiny interface:

```ts
interface SoraTranslator {
  readonly locale: string
  translate(key: string, params?: Record<string, string | number>): string | undefined
}
```

Without a provider they use the built-in English messages. `@your-scope/ui/i18n` adapts a
petite-vue-i18n instance to that interface; `createSoraTranslator` does the same without any library.
Locale files are flat, identical in keys, and published both as strings and precompiled (so an
application can drop the runtime message compiler). See [i18n.md](./i18n.md).

## Forms

`@your-scope/ui/forms` uses Formisch's composables and methods only (its own `Form`/`Field`
components are VDOM SFCs and are never rendered). `useSoraFormField()` returns one object to `v-bind`
on any control; `SoraForm` owns submission; `SoraFormErrorSummary` lists errors. See [forms.md](./forms.md).

## Overlays

| Component           | Platform feature                                                                     |
| ------------------- | ------------------------------------------------------------------------------------ |
| `SoraDialog`        | `<dialog>.showModal()`, `closedby`: top layer, inert page, focus containment         |
| `SoraDrawer`        | `<dialog>.showModal()` (modal) or `popover="manual"` (non-modal), Web Animations     |
| `SoraPopover`       | `popover="auto"` (or `manual`), native invoker trigger, CSS anchor positioning       |
| `SoraDropdownMenu`  | `popover="auto"`, native invoker trigger, `<hr>` separators, roving focus, typeahead |
| `SoraTooltip`       | `popover="hint"`, anchor positioning                                                 |
| `SoraCombobox`      | `popover="manual"` so focus stays in the input                                       |
| `SoraToastProvider` | `popover="manual"` region with two persistent live regions                           |
| `SoraAccordion`     | `<details name>` / `<summary>`, `::details-content`                                  |

Two small composables keep a `v-model:open` boolean and the native element in sync in both
directions ([`use-overlay.ts`](../packages/ui/src/composables/use-overlay.ts)). There is no teleport,
no focus-trap library and no positioning library. Popups are positioned with `position-anchor`,
`position-area` and `position-try-fallbacks`; entry and exit animations use `@starting-style` and
`transition-behavior: allow-discrete`.

### The sheet

`SoraDrawer` is a native sheet, after [vue-native-drawer](https://github.com/gaomingzhao-system/vue-native-drawer)
([`use-sheet.ts`](../packages/ui/src/composables/use-sheet.ts), physics in
[`internal/sheet.ts`](../packages/ui/src/internal/sheet.ts)):

- **Positions are offsets** from fully open towards the sheet's edge; snap points resolve to offsets
  once per size change.
- **Dragging** follows the finger 1:1 and writes at most once per animation frame; coalesced pointer
  samples feed an allocation-free ring buffer that measures the release velocity. Past its range the
  sheet rubber-bands like UIScrollView.
- **Releasing** projects the position forward by its momentum (UIScrollView's deceleration rate); the
  nearest snap point wins, a flick always moves on, and a fast or far enough release dismisses.
- **Settling** is a critically damped spring with a closed form, sampled into Web Animations keyframes
  for the panel, the backdrop, the footer, the page behind it and a parent sheet. They run on the
  compositor (`transform` and `opacity` only). Because the spring is known in closed form, catching
  the sheet mid-flight reads its position and velocity from the spring instead of the computed style,
  and a re-thrown sheet keeps its momentum.
- The panel is promoted to its own layer only while it moves, and listeners are bound with
  `AbortController` signals.

Trigger contract: `SoraPopover` and `SoraDropdownMenu` render their own trigger button by default. It
is a native invoker (`popovertarget`): the browser toggles, light-dismisses and returns focus. A
custom trigger receives explicit `attrs` (including `popovertarget`), `on` and `ref` bindings through
the `custom-trigger` slot; nothing is cloned or injected.

State follows the element ([`use-overlay.ts`](../packages/ui/src/composables/use-overlay.ts)): a popover
closed natively (light dismiss, Escape) reports `toggle` one task later, so closing is mirrored on
`beforetoggle`, synchronously, and a key pressed in between (Escape, then Enter on the trigger) acts on
the real state. Opening is mirrored on `toggle`, once the popover is shown and focus can move into it.

## Reactivity and data

- State that holds a primitive, or is replaced as a whole, is a `shallowRef`; nothing large is ever
  made deeply reactive by the library.
- Lookups by value use a `Map` or a `Set` built once per change of the data (select, combobox,
  checkbox group, accordion, table selection with `Set` intersection and difference), never an array
  scan per render or per keystroke.
- Layout reads happen once per change (the tab marker, the table's scroll region) and are written
  straight to the element, not through reactive state.
- Search helpers reuse one `Intl.Collator` per locale and cache normalised labels.

## Build

- **JavaScript and declarations:** tsdown (Rolldown) with `unplugin-vue`; one entry per manifest
  component; `vue`, the optional peers and `@your-scope/theme` are never bundled. Declarations come
  from the `tsc` generator with Vue support, backed by the TypeScript 7 engine through
  `typescript-native-bridge` (see [dependencies.md](./dependencies.md)).
- **CSS:** the Tailwind CLI compiles `styles/index.css` to `dist/styles.css`;
  `styles/tailwind.css` is copied unchanged ([`scripts/build-styles.ts`](../scripts/build-styles.ts)).
- **Locales:** `?compiled` imports are precompiled with `@intlify/message-compiler` by a small
  Rolldown/Vite plugin ([`scripts/compiled-messages-plugin.ts`](../scripts/compiled-messages-plugin.ts)).

## Tests

| Layer   | Tool                | What it covers                                                                  |
| ------- | ------------------- | ------------------------------------------------------------------------------- |
| Unit    | Vitest (Node)       | Colour maths, theme resolver, internals, i18n, manifest consistency             |
| Browser | Vitest Browser Mode | Every component in Chromium against the sources and the real stylesheet         |
| Types   | vue-tsc             | Must-compile and must-not-compile cases, against sources and built declarations |
| E2E     | Playwright + axe    | The built gallery and the packed consumers                                      |
| Package | scripts             | Vapor proof, export map, isolation, tarballs, consumers, bundle budgets         |

Node resolves `vue` to its CommonJS build, which has no Vapor runtime, so components are only ever
tested in a browser. Browser tests mount with `createVaporApp` through a small helper
([`tests/helpers/mount-vapor.ts`](../tests/helpers/mount-vapor.ts)); there is no VDOM app and no
component test library in the graph. Any `console.warn` or `console.error` during a browser test
fails it, and every E2E test fails on console errors, page errors and failed requests.
